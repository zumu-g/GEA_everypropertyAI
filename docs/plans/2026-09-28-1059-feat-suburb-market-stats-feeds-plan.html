Goal Capsule

Objective. A consumer calling the MCP server can ask for Berwick's month and get a stable, non-empty block of market statistics whose counts reflect what is on the market now, not everything crawled since June, and can see how asking prices moved, how auctions and private sales are converting, and how buyers are behaving.

Means. Repair and complete the listing lifecycle at the shared feed write path, record price observations on change, derive period statistics from the corrected tables into a frozen history table, and surface them through the existing API-route-plus-MCP-tool pattern (KTD1, KTD4, KTD6).

Authority hierarchy. Product requirements (R-IDs) win on behaviour. Key Technical Decisions win on mechanism. Units override neither. Existing response fields are frozen: additive changes only (R1).

Stop conditions. Stop and surface if: a migration cannot be applied idempotently in the Supabase SQL editor; refreshing last_seen_at would deactivate rows of another source (KTD2 guard fails); any backfill would exceed the per-run paid-fetch caps in U6; the coverage guard in KTD2 skips the sweep for most suburbs on two consecutive runs (the crawls are not seeing the market); or the Berwick smoke test cannot produce a non-empty block after U8 lands.

Execution profile. Three phases landed as separate PRs. Phase A must be live and observed for at least two full sweeps per source (a fortnight for REA, whose full sweep is weekly) before Phase C's stats are trusted. sentimentIndex will be null for roughly six months after go-live while real history accrues (KTD7). Tail ownership: the implementer opens each PR; Stuart applies migrations in Supabase and confirms.

Product Contract

Summary

Fix the feed write path so every crawl refreshes last_seen_at, stamps a normalised lifecycle status, counts consecutive misses per source, and marks a listing removed after two misses. Record an asking-price observation whenever a known listing's parsed price differs from the last one seen. Capture each listing's sale method and auction date so auction clearance and private-sale conversion can be reported. Populate listed dates from sources that carry one and fall back to first-seen with the basis labelled. Compute weekly and monthly suburb statistics from the corrected tables, freeze each closed period in a history table, derive a documented 0 to 100 sentiment index, and expose price_changes and suburb_stats as API routes, MCP tools and CLI commands. Apply the same lifecycle and price-history treatment to rentals. Backfill listed dates for five priority suburbs under a fixed cost cap.

Problem Frame

The on-market tables were designed with a lifecycle in mind: they already carry last_seen_at, active, status and listed_date columns, and an expiry routine exists. The lifecycle never runs for sales listings because three of the four live writers omit last_seen_at and active from their upsert payloads and never call the expiry step. Supabase's merge-duplicates upsert only updates the columns present in the payload, so last_seen_at keeps its insert default forever. The result today:

  • 11,866 sales listings, every one flagged active, with last_seen_at equal to created_at on all sampled rows. Rentals do expire, but only the Domain Web Unlocker source and only because that script carries its own source-scoped expiry.
  • No source we crawl returns a listed date for the main sales feeds, so listed_date is null on all 11,866 rows and daysOnMarket cannot be computed.
  • No price observations are kept, so a price cut is invisible once the row is overwritten.
  • The GEA stats pipeline therefore has no defensible active count, days on market, price-cut share or sentiment signal for any suburb.

Two latent hazards shape the fix. The existing expiry routine is scoped by suburb but not by source, so the moment REA and Homely rows start refreshing last_seen_at, the Domain webhook's expiry would deactivate them. And the REA scrape now runs in a cheap new-listings-only mode four days a week, so a listing not seen on those days has not been missed.

Key Decisions

  • Removal is judged per source against that source's own full-sweep runs, not calendar days. (session-settled: user-approved — chosen over a calendar-day rule: REA new-only runs and dropped GitHub schedules would otherwise count as misses.) Governs R4, R5.
  • A closed period's statistics are computed once and frozen; the open period recomputes on each call. (session-settled: user-approved — chosen over recomputing every period from live data: the feed changes retroactively as lifecycle catches up.) The freeze point is sixty days after period end, so late Valuer General sales and sold reconciliation settle first. Governs R17, R18.
  • Listed date keeps its source when a source provides one and otherwise falls back to first-seen, with the basis labelled. (session-settled: user-approved — chosen over leaving null: none of the three main feeds carries a listed date today.) Governs R8, R9.
  • Enquiry and view counts are schema-ready but not populated. (session-settled: user-approved — no crawled source exposes them.) Governs R23.
  • Backfill is capped to active listings in the five priority suburbs. (session-settled: user-approved — chosen over every historical row: paid per-page fetches.) Governs R10.
  • The existing status field keeps its raw portal text; the normalised lifecycle lives in a new field. Changing status's meaning would break the frozen response contract. Governs R1, R3.

Requirements

Compatibility

  • R1. Every existing field in on_market_listings, rental_listings, sold_sales and their API routes keeps its name, type and meaning. New data arrives only as new fields or new tools.
  • R2. Migrations are additive and idempotent, runnable in the Supabase SQL editor, and mirrored into src/lib/db/schema.sql.

Listing lifecycle (sales and rentals)

  • R3. Every crawl that sees a listing refreshes its last_seen_at, sets it active, and stamps a normalised lifecycle status of active, under_offer, sold or withdrawn derived from the source's status text.
  • R4. A listing absent from a full-sweep run of its own source, in a suburb that run covered completely, gains one miss, at most one per calendar day. A listing seen again resets to zero misses.
  • R5. At two consecutive misses the listing is marked inactive with removed_at set to that run's start. Lifecycle becomes withdrawn unless a sold signal (R7) or a matching sale (R21) reclassifies it as sold. A rental at the same point gains leased_at instead.
  • R6. on_market_listings and rental_listings return only active rows by default and return inactive rows when includeInactive=true. Each row exposes lifecycleStatus, removedAt and, for rentals, leasedAt.
  • R7. A source that reports a sold or under-offer state sets that lifecycle status on the row when seen, before any miss counting.
  • R24. A closed listing seen again reopens: it becomes active with zero misses, its removal or lease timestamp clears, and a new campaign start is recorded that becomes its days-on-market basis.
  • R25. Each sales listing carries sale_method of auction, private or unknown, and auction_date when one is stated, both derived from the source's price and status text on every crawl.

Listed date and days on market

  • R8. When a source carries a listed date the row stores it with listed_date_source naming the source. Otherwise listed_date stays null and first-seen (created_at) is the fallback basis.
  • R9. daysOnMarket is computed on read: today minus the basis date for active rows, and the closing date (removed_at, leased_at or matched sale_date) minus the basis date for closed rows. The basis is listed_date when set, else the current campaign start (R24), else first-seen. Each row states daysOnMarketBasis as listed or first_seen.
  • R10. Domain listed dates are captured on every daily crawl from the search result itself at no extra cost. A one-off probe of the REA per-property call decides whether REA listed dates can be backfilled for active listings in Berwick, Officer, Clyde North, Narre Warren and Pakenham, stopping at the cost cap in U6.

Asking-price history

  • R11. A listing_price_history table records, per listing identity (table, raw address, source), the observed time, display price, price low, price high and listing URL. A row is written on first sight and whenever a crawl sees a parsed price (low, high) different from the most recent record; display text is compared only when neither observation parses to an amount, and sold or under-offer rows are not diffed.
  • R12. Each listing in on_market_listings and rental_listings carries priceHistory[], oldest first.
  • R13. A price_changes(suburb, state, sinceDays) tool returns listings whose asking price changed inside the window, with previous and current display price, previous and current midpoint, the percentage change on the midpoint, and the change date. Only changes with a non-null, non-zero percentage are returned. sinceDays is clamped to 1 to 365.

Suburb statistics

  • R14. A suburb_stats(suburb, state, period, asOf) tool, with period as month or week and asOf defaulting to today, returns the block for the period containing asOf.
  • R15. The block contains: activeListings, newListings, medianAsking, medianDaysOnMarket, priceCutCount, priceCutMedianPct, withdrawnCount, salesCount, medianSalePrice, medianSalePriceHouse, monthsOfSupply, saleToListRatio, auctionsHeld, auctionsCleared, auctionClearanceRate, privateSalesClosed, privateSalesSold, privateSaleConversionRate, rentalListings, medianRent, sentimentIndex and sentimentBasis. saleToListRatio is the median of sale price over the last asking midpoint observed before the sale, across period sales matched under R21, and null under five matches.
  • R26. auctionClearanceRate is auctionsCleared over auctionsHeld, where an auction is held when a listing's auction_date falls in the period, and cleared when that listing is sold by source status or by an R21 sale match within 14 days after the auction date. privateSaleConversionRate is privateSalesSold over privateSalesClosed, where a private-sale listing closes in the period when it reaches sold or withdrawn. Each rate is null under five in its denominator and the counts are always returned.
  • R16. The response also carries the same block for the prior period and for the same period one year earlier, under prior and yearAgo, each null when no data exists.
  • R17. A closed period is served as provisional, recomputed on call, until sixty days after its end, then written once to suburb_stats_history and served from there on every later call.
  • R18. A period that closed before the history table existed is computed from current data on first request, stored, and flagged reconstructed: true.
  • R19. sentimentIndex is an integer 0 to 100 built from sale-to-list ratio, months of supply, price-cut share, median days on market and auction clearance rate, each scaled against that suburb's trailing range of frozen, non-reconstructed months, and sentimentBasis documents each input, its range, its scaled value and the formula. It is null with a reason when fewer than two inputs are available or fewer than six such months exist.

Sold feed and rentals

  • R20. settlementDate is returned on sold records wherever the Valuer General row carries it. This is already wired; the requirement is coverage verification, not construction.
  • R21. A sold record gains firstListedDate and daysOnMarket by matching a listing on address slug whose first-seen or listed date precedes the sale date by no more than 400 days.
  • R22. Rentals receive R3 to R5, R8, R9, R11 and R12 with weekly_rent as the price and leased_at as the closing timestamp.
  • R23. Columns enquiry_count and view_count exist on both listing tables; no current writer populates them and the sentiment index does not read them in this plan.

Acceptance Examples

  • AE1. Covers R4, R5. A Berwick REA listing is present in Monday's full sweep, absent from the next Monday's full sweep (miss 1), and absent again the Monday after (miss 2). Only then is it inactive with removed_at set. The Tuesday to Friday new-only runs in between change nothing, and a second full run on the same day as a miss adds no further miss.
  • AE2. Covers R11, R13. A listing seen at "$850,000 - $900,000" on 1 September and "$820,000 - $860,000" on 15 September has two history rows and appears in price_changes("Berwick","VIC",30) with a midpoint change of minus 4.0%.
  • AE3. Covers R17, R18. Calling suburb_stats("Berwick","VIC","month","2026-08-15") on 20 October computes August from current data and returns it with provisional: true; from 31 October the nightly job freezes it with reconstructed: true, and every later call returns the identical stored block.
  • AE4. Covers R19. A suburb with only 5 months of history returns sentimentIndex: null and sentimentBasis.reason: "insufficient-history" while every other statistic is populated.
  • AE5. Covers R24, R9. A house withdrawn in March and re-listed by the same agency in September reopens as active on the first crawl that sees it, shows removedAt null, and reports days on market from September, not March.
  • AE6. Covers R25, R26. Twelve Berwick listings show "Auction Sat 14 Nov" during November; by 28 November eight are sold by source status or matched to a sale, so November returns auctionsHeld 12, auctionsCleared 8 and auctionClearanceRate 0.67. Three auctions in a week give a null weekly rate with counts still returned.

Planning Contract

Key Technical Decisions

  • KTD1. One shared feed-write module for the three scripts. A new scripts/lib/feed-write.mjs owns the upsert payload stamping (last_seen_at, active, lifecycle_status, miss_count: 0), the price diff and history insert, and the post-run sweep. The Domain Web Unlocker, REA and Homely scripts call it instead of posting to PostgREST themselves. The TypeScript path in src/lib/db/queries.ts (Domain webhook, domain-apify, 205 rows, effectively dormant) gets only the source-scoping guard in KTD2 so it cannot damage other feeds. Rationale: the scripts already share scripts/lib/feed-health.mjs and healthcheck.mjs; one implementation avoids three drifting copies.
  • KTD2. Expiry is scoped by source and driven by miss counting against verified full sweeps. expireNotSeen gains a mandatory source argument. A full sweep of a suburb means the crawl paginated that suburb until a page returned fewer than its page size; a suburb that hit the page cap is truncated and is excluded from the sweep. The sweep, per source and per completely covered suburb, increments miss_count on active rows with last_seen_at before run start and miss_marked_at null or older than twenty hours, stamps miss_marked_at, resets both on rows seen, and closes rows (active=false, removed_at or leased_at, lifecycle_status) when miss_count reaches 2. Coverage guard: when a run saw fewer than half the active rows of that source in a suburb, the sweep skips that suburb and records it. Only REA runs with REA_MODE=full sweep; Domain and Homely daily runs sweep. Rationale: today no crawl sees a whole suburb (REA fetches 25 per suburb, Domain and Homely one page), two schedulers can fire one feed on one day, and GitHub silently drops runs. A miss must mean "a complete crawl looked and did not find it".
  • KTD3. Lifecycle status and sale method are new columns mapped from source text by one pure function. status stays raw. Lifecycle: text containing "under offer" or "under contract" gives under_offer; "sold" or Homely's soldOn gives sold; everything else while active gives active; removal gives withdrawn unless a sold signal exists. Sale method: price or status text containing "auction" gives auction and parses a day-month date into auction_date (year inferred as the next occurrence); a stated dollar amount or "private", "for sale", "offers" gives private; otherwise unknown. Once auction the method sticks for the campaign even if the text later changes. Rationale: R1 freezes status; the production snapshot shows "Auction Sat 6 Jun" style text is the only auction signal available.
  • KTD4. Price history is keyed on listing identity (table, raw address, source) and written by diffing parsed prices in the write module, not by a database trigger. The module selects the latest history row per identity for the batch in one query, compares (price_low, price_high) when the new observation parses an amount and normalised text only when neither side parses, skips rows mapped sold or under offer, and inserts rows for first sight and for changes. Rationale: listing URL is nullable and changes on relist; auction dates and status text change weekly without a price change; testable in the existing .test.mjs pattern.
  • KTD5. Days on market is derived on read, never stored. The API routes compute it from listed_date, else campaign_started_at, and the closing timestamp. Rationale: a stored value goes stale daily; the basis label (R9) is cheap to compute alongside; the campaign start survives a relist (R24).

Key Technical Decisions (continued)

  • KTD6. Suburb statistics are computed by one module, src/lib/stats/suburb-stats.ts, reusing the period and median helpers in src/lib/values/suburb-values.ts, and persisted to suburb_stats_history on the natural key (suburb, state, period_type, period_start). Frozen periods are read from the table; the open period and any closed period younger than sixty days are recomputed on call and upserted with provisional=true. A nightly job freezes periods whose settle date passed yesterday for the service-area suburb list in src/data/casey-cardinia.ts (about 80 suburbs, so under 200 rows a night). On-demand calls reject suburbs outside that list and dates outside the data range, so persistence is bounded. Rationale: R17 and R18; Valuer General sales arrive quarterly and sold reconciliation runs nightly; migration 014 is the schema model.
  • KTD7. Sentiment index formula. For each of five inputs (sale-to-list ratio, months of supply, price-cut share, median days on market, auction clearance rate) take the suburb's trailing twelve frozen months with reconstructed=false, compute min and max, scale the current value to 0 to 1 within that range, invert months of supply, price-cut share and days on market so higher means hotter, and average the available inputs. Multiply by 100 and round. An input whose range is degenerate (max equals min), or whose current value is null (a clearance rate under five auctions), is dropped. Fewer than two inputs, or fewer than six qualifying months, returns null with reason insufficient-history. The formula string and every input's raw value, range and scaled value are returned in sentimentBasis. Rationale: reconstructed months count every pre-go-live row as active and have zero price cuts, which would pin the range and bias the index hot for a year.
  • KTD8. New endpoints follow the existing route-plus-MCP-plus-CLI pattern and are added to the middleware matcher. Each new tool is an API route under src/app/api, a client method and response type in services/everypropertyai/src, a server.tool registration and a commander command. Rationale: a route absent from config.matcher in src/middleware.ts is unauthenticated.
  • KTD9. Paid-fetch caps. Full-sweep pagination: Domain and Homely at most 20 pages per suburb per run through Web Unlocker; REA full mode pages until a short page, expected near 3,000 items a week (about US$9, roughly US$40 a month against the US$100 Starter cap). REA listed-date probe: one batch of 20 through the per-property call, then at most 1,500 items at US$0.003 only if the probe returns a date. No Domain per-page backfill: the daily crawl already carries the listed date. Every run writes fetched, dated, failed and estimated cost to feed_runs.

High-Level Technical Design

Listing lifecycle state machine (R3 to R7, KTD2, KTD3)

A rental follows the same shape with leased_at in place of removed_at and no under_offer or sold states; its inactive state is withdrawn, read by consumers as leased.

Per-run write path (KTD1, KTD2, KTD4)

Step 6 is the only step that can deactivate a row and it always carries a source. The Domain webhook route keeps its own TypeScript path but its expireNotSeen call gains the same source scope.

Assumptions

  • Once paginated (U3), a run that ends on a short page has seen every listing the portal shows for that suburb. A truncated or blocked suburb is excluded from the sweep; the feed-health blocked status already exists to signal a blocked run.
  • Auction outcomes are inferred from lifecycle, not from a portal result field: a listing marked auction that is sold within 14 days of its auction date cleared; one still active or withdrawn after that did not. Sold prior and sold after are both counted as cleared.
  • Address slug is a reliable join key between property_sales and property_listings; both tables carry it and the sold-sales enrichment already relies on it.
  • The GEA stats pipeline computes deltas itself from prior and yearAgo; the tool does not return deltas.
  • Weeks are ISO weeks starting Monday, in Australia/Melbourne time; months are calendar months in the same zone.

U1. Migration 015: lifecycle, price history, stats history

Goal
Add every column and table the later units write, idempotently, with service-role RLS. property_listings and property_rentals are the tables behind the on_market_listings and rental_listings tools named in the requirements.
Requirements
R2, R3, R5, R8, R11, R17, R22, R23, R24, R25
Dependencies
None
Files
src/lib/db/migrations/015_listing_lifecycle_price_history_stats.sql (new), src/lib/db/schema.sql, scripts/verify-rls.mjs, src/lib/db/__tests__/migration-015.test.ts (new, parses the SQL for required statements)
Approach
  1. On property_listings and property_rentals add lifecycle_status TEXT NOT NULL DEFAULT 'active' with a CHECK on the four values, miss_count SMALLINT NOT NULL DEFAULT 0, miss_marked_at TIMESTAMPTZ, removed_at TIMESTAMPTZ, campaign_started_at TIMESTAMPTZ NOT NULL DEFAULT now() (backfilled from created_at), listed_date_source TEXT, enquiry_count INTEGER, view_count INTEGER. Sales listings also gain sale_method TEXT NOT NULL DEFAULT 'unknown' with a CHECK on (auction, private, unknown) and auction_date DATE; rentals gain leased_at TIMESTAMPTZ.
  2. Create listing_price_history: id, table_name CHECK in (listings, rentals), raw_address, source, listing_url (nullable, informational), observed_at, display_price, price_low, price_high; index on (table_name, raw_address, source, observed_at desc).
  3. Create feed_runs: id, category, source, mode, run_start, run_end, status, seen, new_rows, priced, miss1, closed, skipped_suburbs, fetched, dated, failed, est_cost_usd, notes JSONB; index on (source, run_start desc). feed_health stays as is so freshness and digest jobs keep working.
  4. Create suburb_stats_history: suburb, state, period_type CHECK (week, month), period_start DATE, period_end DATE, stats JSONB, provisional BOOLEAN, reconstructed BOOLEAN, computed_at, schema_version; UNIQUE (suburb, state, period_type, period_start). Model on migration 014.
  5. Partial index on each listing table: (suburb, state) WHERE active, and (source, suburb, active, last_seen_at) for the sweep.
  6. RLS per migration 011: enable, one service-role policy inside the duplicate_object guard. Add all three new tables to verify-rls.mjs.
Patterns
Migration 014 header, CHECK and UNIQUE style; migration 011 RLS block.
Test scenarios
  • The SQL file contains IF NOT EXISTS on every CREATE and ADD COLUMN.
  • Running the file twice against a scratch schema succeeds (documented manual check).
